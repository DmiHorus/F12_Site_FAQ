## 3. Вопросы, которые ты обязан задать мне до начала

Сначала определи характеристики ПК (ОС, процессор, объём ОЗУ, наличие GPU или Apple Silicon, свободное место на диске), потом спроси меня:

- ○ **A. Локальный поиск + локальная LLM.** Локальная модель эмбеддингов находит ответы, локальная LLM (например, через Ollama) формулирует ответ по найденному и учитывает историю диалога. Ближе всего к уроку, но требует ресурсов.

- ○ **C. Как в уроке, через OpenAI.** Нужен `OPENAI_API_KEY`, запросы уходят в облако. Противоречит условию «только на этом ПК».

К каждому варианту приложи свою оценку: потянет ли его этот ПК и сколько места займут модели. Архитектура из раздела 5 поддерживает все три варианта переключением в `.env`, режим B реализуется всегда как базовый.

## 4. Выбор модели (обязательный этап с обоснованием)

Модель выбираешь ты и обосновываешь выбор. Условия:

- работает локально, только на этом ПК; после первого скачивания весов интернет не нужен (проверь запуском с `HF_HUB_OFFLINE=1` или отключённой сетью);
- назначение — модуль поиска по FAQ на странице сайта и в чат-виджете;
- язык запросов и базы — русский, встречаются латинские названия и аббревиатуры (MNWHL, MCP, RAG, OIDC, MAX, СЭДО);
- база маленькая (40 записей), поэтому важны качество на русском, размер и скорость на CPU, а не масштабируемость.

Как выбирать:

1. Составь шорт-лист из 3 локальных моделей эмбеддингов с поддержкой русского языка и разным размером. Актуальные названия, размеры, лицензии и требования (например, префиксы `query:` / `passage:` у некоторых семейств) проверь по карточкам моделей, не по памяти.
2. Напиши `scripts/eval_retrieval.py` и прогони каждую модель на `data/faq_eval.json`. Метрики: Recall@1 и Recall@3 на `in_scope`, доля верных отказов на `out_of_scope`, среднее время запроса, размер модели на диске, пик ОЗУ.
3. Подбери порог сходства для отказа по тому же набору.
4. Для сценария A так же выбери локальную LLM под ресурсы ПК и проверь, что она отвечает по-русски и не добавляет фактов сверх контекста.
5. Запиши результат в `docs/MODEL_CHOICE.md`: характеристики ПК, таблица сравнения, выбранная модель, порог, причины выбора, ограничения.

Целевые пороги на `faq_eval.json`: Recall@1 ≥ 0,85; Recall@3 ≥ 0,95; верных отказов на `out_of_scope` не меньше 4 из 5. Если пороги не достигаются ни одной моделью — не подгоняй набор, а покажи мне цифры и предложи решение.

### 5.1. `backend/app.py` (сейчас: FastAPI с `/chat` и `/health`)

Что не так в текущем коде и что сделать:

- При импорте модуль падает с `RuntimeError`, если нет `OPENAI_API_KEY`, и сразу создаёт клиента OpenAI. → Ключ нужен только в режиме OpenAI. Настройки читать из `backend/config.py`.
- `ChatRequest` содержит только `message` и `top_k`, истории диалога нет, хотя урок требует память. → Добавить `session_id: str | None`. История хранится на сервере в `memory.py` (словарь в памяти процесса, последние 6 реплик на сессию, ограничение числа сессий).
- Контекст передаётся в LLM без проверки релевантности, отказ возложен на модель. → Отказ решает код: если лучшая оценка сходства ниже порога, вернуть фиксированный текст: «В базе знаний нет ответа на этот вопрос. Напишите нам: hello@mnwhl.ru».
- `embed_text` жёстко привязана к `text-embedding-3-small`. → Вынести в `embeddings.py`.
- `CORSMiddleware` с `allow_origins=["*"]` и `allow_credentials=True`. → Сайт и API теперь на одном origin; оставить только `http://localhost:8000` и `http://127.0.0.1:8000` из настроек.
- Нет страниц сайта. → Добавить `Jinja2Templates` и `StaticFiles`; маршруты `/`, `/cases`, `/faq`, `/contacts`.

Контракт API (на него опираются `TEACHER_CHECK.md` и тесты, не меняй без согласования):

```text
GET  /health
     → {"status":"ok","faq_count":40,"embedding_model":"...","answer_mode":"extractive|local_llm|openai"}

POST /chat   {"message":"...", "session_id":"необязательно", "top_k":3}
     → {"answer":"...", "found":true|false, "session_id":"...", "answer_mode":"...",
        "context":[{"id":"faq-015","question":"...","category":"...","score":0.87}]}
     пустое сообщение → 400

GET  /api/faq/search?q=...&top_k=5
     → {"query":"...", "results":[{"id":"...","question":"...","answer":"...","category":"...","score":0.87}]}

GET  /api/faq          → все 40 записей (для страницы FAQ)
```

Логика `/chat`:

1. Получить историю по `session_id` (нет — создать новый id).
2. Сформировать поисковый запрос. Короткая реплика-продолжение («А какие результаты?») ищется вместе с предыдущим вопросом пользователя. В режиме с LLM допустимо переформулировать запрос моделью.
3. Найти `top_k` записей с оценками сходства.
4. Лучшая оценка ниже порога → `found=false` и текст отказа.
5. Иначе ответ по режиму:
   - `extractive` — текст `answer` лучшей записи без изменений;
   - `local_llm` / `openai` — LLM получает системный промпт, историю и найденные записи. Системный промпт: отвечать кратко, по-русски, только по контексту; нет ответа в контексте — сказать об этом и дать `hello@mnwhl.ru`; не называть цены, сроки и факты, которых нет в контексте. `temperature` не выше 0,2.
6. Сохранить реплики в историю и вернуть ответ.

## 7. Секреты

В режимах A и B секреты не нужны. Если что-то всё же понадобится (например, `OPENAI_API_KEY` для режима C или токен для скачивания модели):

1. остановись;
2. назови точные имена переменных и для чего каждая нужна;
3. попроси меня положить значения в `.env` и подтвердить;
4. продолжай только после подтверждения.

Не придумывай значения, не используй заглушки вместо ключей, не пиши секреты в код, логи, коммиты и `.env.example`. Перед коммитом проверь, что `.env` не отслеживается.

## 8. Commit и push

После локальной проверки всех этапов:

1. `git status` и `git diff --stat`: в коммите нет `.env`, `venv/`, кеша моделей, индекса, `MNWL/`, `FAQ_SOURCES.md`.
2. Коммит(ы) с понятными сообщениями, например: `feat: FAQ-ассистент Минвайл — локальный поиск, сайт с кейсами, чат-виджет (v1.0.0)`.
3. `git push` в мой удалённый репозиторий (ветка `main`). Без `--force`. Если push отклонён — сначала `git pull --rebase`, при конфликтах остановись и спроси меня.
4. Итоговый отчёт: адрес репозитория и хеш коммита, выбранный сценарий и модель, метрики, что не сделано или сделано иначе и почему, список команд для проверки.
